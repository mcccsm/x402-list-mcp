# x402-list

## What x402-list is

x402-list is a directory of services that accept x402 payments. Its distinctive, defensible data is **on-chain-verified settlement volume per facilitator**, not self-reported figures. Listed services are continuously health-monitored for uptime, response time, and live status. This MCP server is a read-only wrapper over the public x402-list API; it needs no API key.

## Money units (read this first)

**All `*_usd` fields are decimal US dollars and are used as-is. There is no cents conversion.** For example `min_price_usd: 0.001` means one tenth of a cent, and `volume_usd_all: 1542635.84` means about 1.54 million dollars. The service-detail `pricing[].price` field is an atomic on-chain token amount (a uint256 string), NOT dollars; only `price_usd` is the dollar figure. Never rescale either one.

## Tool guide (when to use each)

- `x402_search_services`: find and filter services by free-text query, category, network, and status; sort by newest, uptime, cheapest, or endpoint count. Start here for discovery. Add `signable: true` when you intend to pay with a standard x402 client and want only services whose last observed 402 envelope carries the EIP-712 domain parameters needed to sign (`signable: false` returns the opposite set; a service whose latest assessment has not measured that check matches neither value, so omit the parameter to see it).
- `x402_get_service`: deep-dive one service by slug. Returns every endpoint, per-endpoint USD pricing, uptime windows (24h/7d/30d/90d), accepted networks, and the settlement asset.
- `x402_find_best_service`: get a ranked recommendation for a need, computed server-side (GET /api/v1/best). Ranks mostly by reliability, x402 compliance and price (status, verified, uptime_24h, response time, USD price), filtered by category and network, with a small (~10%) weight on per-service on-chain traction (settlement volume, tx count, unique buyers - a conservative undercount). Traction never dominates; a shared payout has only its VOLUME attributed pro-quota (counts stay whole operator-level integers), and an unmeasured-network service, or a shared member whose probe is failing, carries no traction term at all. The response carries `ranking_version`, **3** today, plus a `units` map with every scoring caveat in full; scores stored under an earlier generation are NOT comparable with these, because the math moved twice. Generation 2 introduced the compliance cap: the compliance term is the share of deterministic conformance checks the service passes, capped at 0.6 (the floor of the C band) when at least one of its EVM routes is missing the EIP-712 domain parameters a standard x402 client needs in order to sign a payment, which is a fact about the envelope on the wire and not a judgement on the merit of the service. Generation 3 added the anti-wash rules on the traction term: an absolute $10 floor on 30d settlement volume, under which the term scores 0 because sub-floor volume is indistinguishable from dust and must not move rank; a discount on a payout concentrated in one buyer, up to half the traction term when a single buyer accounts for all of it, since one buyer is one relationship and not broad demand; and a 0 term, instead of a renormalization, for a service that publishes no mappable payTo, so hiding the payout address no longer beats having a measured one.
- `x402_check_health`: live status. With no slug, a directory-wide snapshot (online/degraded/offline/unknown counts plus per-service status). With a slug, that service's status, uptime windows, response time, consecutive failures, and recent daily uptime snapshots.
- `x402_facilitator_volumes`: the headline metric. Per-facilitator settlement volume (24h/7d/30d/all) in USD, transaction counts, and an `on-chain` vs `listed` verification flag. Optional daily timeseries and per-chain breakdown.
- `x402_change_events`: the drift feed, free and read-only. What the monitor observed changing on listed services, most recent first, in exactly three event types: `payto_changed` (the payout address set changed), `price_changed` (at least one endpoint changed price), `schema_changed` (the 402 envelope gained or lost accepts entries or priced endpoints). Reach for it before trusting anything you cached about a service, and right after a payment failed for no obvious reason. Filter with `service` (the listing slug, the same slug `x402_get_service` takes), `type`, and `days` (1 to 365, default 90); page with `page` and `per_page` (up to 100). **The slug parameter is named `service`, not `slug`**: pass the wrong name and the API answers with the whole unfiltered feed, silently and with no error, so check `filters_applied` in the response before reading the result as one service's history. `total` is the server's count over the whole filtered window, not the length of the page you are holding (`returned` is that). Two units traps: the prices inside an event are ATOMIC token amounts, never dollars, and every payTo is masked by the API by design, so the feed tells you THAT the payout address changed, never what it changed to.
- `x402_assess_services`: PAID ($0.25 USDC on Base, x402). A fresh on-demand AI comparison of a shortlist of listed services for a stated need. This is a pass-through: it never holds keys, never signs, and never settles. Call it once without `payment_signature_b64` to receive the x402 payment challenge verbatim, sign accepts[0] client-side with your own wallet, then call again with the same question and services plus `payment_signature_b64` to receive the report and a settlement receipt. It charges only for the fresh reasoning, never to read an already-computed assessment (that stays free on `x402_get_service`); a run that cannot be produced answers before settling, so you are never charged, and there is no refund. Optionally add a `probe` target `{ slug, endpoint_path? }` to also test one listed service live: when the server has probing armed the price becomes $0.25 plus that endpoint price X (non-refundable), and the report gains a `probe_report` block with a verdict and truncated extracts, never the verbatim third-party body.

## The honesty guard

Keep two on-chain signals distinct. **Facilitator volume** (`x402_facilitator_volumes`) is aggregated per facilitator and is the headline metric. **Per-service traction** (the `traction` block on a service, and a ~10% weight inside `x402_find_best_service`) is measured over that service's own payTo via recognized settlers and is a deliberate **conservative undercount** - never an upper bound, never an estimate. When a payTo is shared across services (`shared_payout: true`), only settlement VOLUME is attributed pro-quota, the operator-level volume over that address divided across the services sharing it, which is a declared convention and not an individually observed measure, while transaction count and unique buyers stay whole operator-level integers, never fractional; when a service sits on a network we do not measure, or is a shared-payout member whose probe has been failing, it carries no traction term at all and the other weights are renormalized over it. Do not present shared, pro-quota or unmeasured volume as a single service's revenue. If asked "which service does the most volume", show the measured `traction` where it exists, flag the undercount and any shared/unmeasured caveat, and offer facilitator volumes (via `x402_facilitator_volumes`) for the ecosystem aggregate.

## Typical workflows

- "Find me a cheap, reliable image-generation x402 API on Base" -> `x402_find_best_service` with category, network `Base`, your need as `q`, and `prefer: cheapest`, then `x402_get_service` on the top pick.
- "Is service X healthy?" -> `x402_check_health` with `slug: X`.
- "Which x402 facilitators are real (have on-chain volume)?" -> `x402_facilitator_volumes` with `timeframe: 30d`, then read each `verification` flag.
- "I integrated service X last month and the call just started failing / costing more" -> `x402_change_events` with `service: X` and a `days` window that covers the gap, then read the newest `price_changed` or `schema_changed` event and re-check the current record with `x402_get_service`.
- "Is it still safe to pay this service?" -> `x402_change_events` with `service: X` and `type: payto_changed`: a recent payout change is the signal to re-verify before sending money, and the addresses themselves come back masked, so verify against the live 402 envelope rather than against this feed.
